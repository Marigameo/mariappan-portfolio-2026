Report Builder

AI-generated HTML insight reports built inside the global chat. The report lives in the chat's slot canvas as a report_canvas slot (preview + code tabs in a floating card), the insight is bound to the conversation as a workflow_execution_resource, and the report_builder skill rewrites the file via read_file / update_file. There is no separate Report Studio page or report-builder agent any more. The skill prompt is the source of truth for what a report should look like — the page here is the intent behind it.

How it works

End-to-end, all inside the global chat at /ui/chat/:executionId:

  • Four entry points. (a) The Reports page creates a bare HTML insight, triggers the global chat workflow with the insight attached as { resource_type: 'INSIGHT', resource_id }, and navigates to /ui/chat/<execId> with reportInsightId + source_report context in nav state. (b) The report viewer's "Customize in Studio" opens a fresh chat thread with the insight bound and the report_builder badge pinned. (c) The /report_builder slash badge in any chat — on a fresh thread the client creates the scaffold inside onTriggerWorkflow and attaches it at trigger time; mid-thread, onBeforeSend creates the scaffold and POSTs the attach endpoint before the message is sent. (d) Reopening a thread with an INSIGHT resource auto-opens the preview.
  • Resource binding. The backend persists the link in workflow_execution_resource AND writes /reports/<insight_id>/index.html into the sandbox before the trigger/attach response returns — the agent's first read_file always lands a real file. Reads need no dedicated API: the single-execution GET already serializes workflow_execution_resources.
  • The report canvas slot (ReportCanvasSlot, experience report_canvas) is host-driven: HomePage mounts it from the conversation's binding (boundInsightId) — it is not an agent-emitted message chip. It registers with the slot-canvas store, opens immediately on bind even during history hydration (ignoreSuppressAutoOpen), and portals a preview/code body (iframe srcDoc + syntax-highlighted source) into the canvas's floating card. Reopen (after the user closes it, or a behaviour slot takes the canvas) comes from the side SlotNavigator rail — the same trigger every other slot uses — not a bespoke pill.
  • Agent awareness. The chat sends { source_report: { insight_id, display_name, url } } as UPDATE_CONTEXT before the message that needs it — the contract the skill documents. The prompt itself is prefixed with /report_builder so the server-side get_skill tool pulls the skill into context.
  • After every execute_tools settles, HomePage invalidates ["insightHtml", id] and ["insights"]; the slot refetches the new HTML (the hasEverLoadedHtml latch keeps the canvas mounted — no splash regression). update_file already mirrors to insight.html_content, so no client /sync is needed.

Report threads are ordinary global-chat threads: one agent, one history, one model. The old Report Studio routes redirect to the report viewer.

API contracts

POST /api/v1/insight — HTML variant

{
  "insight": {
    "display_name": "Untitled report",
    "html_content": "<!DOCTYPE html>…"
  }
}

Server stores it with type = HTML, status = READY. Unchanged.

POST /api/v1/internal/trigger_chat_workflow

{
  "trigger_workflow": {
    "workflow_instance_id": "…",
    "resources": [{ "resource_type": "INSIGHT", "resource_id": "…" }]
  }
}

When resources is present, the server validates tenant ownership, persists workflow_execution_resource rows, and runs syncInsightToSandbox for each resource — all within the request, before responding.

POST /api/v1/workflow_instance/:wiId/workflow_execution/:weId/workflow_execution_resource

{
  "resources": [{ "resource_type": "INSIGHT", "resource_id": "…" }]
}

Attaches resources to an existing execution (mid-thread /report_builder). Validates tenant ownership, dedupes against already-attached rows, persists, and runs syncInsightToSandbox — all inside the request, so a send awaited on this call cannot race the agent's read_file. Returns 201 with the full resource set. Idempotent for repeats.

GET /api/v1/workflow_instance/:wiId/workflow_execution/:weId

Already serializes workflow_execution_resources — the client reads the binding off it on thread open (no polling; resources only change via explicit attach).

POST /api/v1/insight/:insight_id/sync

Still exists as a manual recovery hatch but is no longer called from the client.

POST /…/execute_tools

Unchanged. The agent's update_file writes the sandbox file AND mirrors to insight.html_content; the host refetches via cache invalidation in onAfterExecuteTools.

Trade-offs worth knowing

  • Sequential create + trigger/attach — the resource needs the new insight id, so creation can't run in parallel. The server's sandbox sync happens inside the trigger/attach request, which is also what makes the await-before-send guarantee possible.
  • No client /sync after tool turns — update_file writes the sandbox file AND mirrors to insight.html_content. Re-syncing would re-upload the same bytes and pay a Daytona reconnect for nothing.
  • Report-specific logic lives in the host (HomePage), not in <Chat /> — the chat exposes generic hooks (canvasSlot, trigger meta, onBeforeSend); ai-elements stays feature-free.
  • Agent awareness is client-context only — no server-side PLATFORM_CONTEXT injection at attach time, because updateChatContext overwrites the last PLATFORM_CONTEXT row; two writers on that channel would clobber each other.
  • Reports build on the global agent's model — the old report-builder agent's pinned model is gone with the agent. One agent, one config.
  • /insight/:id/sync endpoint kept as a manual recovery hatch even though the client no longer calls it.
  • Old report-builder threads are unreachable by design — the agent rows stay in the DB (rollback = re-point the client), but no UI lists them.

Failure modes

StageWhat the user sees
Create-insight failure (Reports)"Failed to start report creation" toast, submit re-enabled. Retry reuses the already-created insight if the create had succeeded.
Trigger failure (resource validation or sandbox sync)Same toast. Surfaces on the Reports page before navigation, so retry doesn't leave a half-built session.
Mid-thread attach failure (onBeforeSend)"Failed to prepare your message" toast; the message is not sent, the badge stays attached, the typed bubble remains for retry.
Initial HTML fetch failureSlot stays on splash; TanStack retries on next focus.
Insight deleted / not HTML"Report not found" empty state inside the slot.
execute_tools failure during a chat turn"There was a problem executing tools" toast; slot keeps the prior HTML.
Thread deleted from the sidebarWorks — deleteWorkflowExecution destroys the resource rows first (non-cascading FK would otherwise 500).
Tenant without a sandboxTrigger/attach 400s with a clean rollback; PostHog report_builder flag gates the entry points.

Out of scope

  • Server-side enforcement of the bootstrap template (client owns the scaffold).
  • Real-time HTML streaming during the agent's edit — we wait for execute_tools to settle, then refetch.
  • Multi-user collaboration on a single report.
  • Diffing / history of HTML revisions (backend keeps latest only).
  • Backfill / migration of pre-unification report-builder threads (intentionally orphaned).
  • Retiring the dev seed script's report-builder setup (bootstrap_ui_chat_agent.ts) — deferred cleanup.
  • Multi-report tabs in the canvas (one report per chat, one open slot at a time; reopen via the side navigator).
